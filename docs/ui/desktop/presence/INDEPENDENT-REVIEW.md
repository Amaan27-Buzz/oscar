## Professional comparison

The distinctive element is OSCAR's recognizable offset shell/puck and independent compact presence. The single writing sheet is conventional but effective; the white status plaque, technical footer and broad focus halo are less resolved. A professional standard also requires dependable immediate input, visible outcomes and recoverable dismissal, which the two native P1 cases fail.

For interaction references, [Microsoft's flyout guidance](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/dialogs-and-flyouts/flyouts) documents Escape dismissal and deliberate focus/input handling. [Raycast's search-bar documentation](https://manual.raycast.com/search-bar) describes compact expansion and a focused input on invocation. These inform review questions, not a requirement to copy their appearance or exact dismissal policy. OSCAR's automatic editor focus remains unverified.

For character craft, [Disney Animation's process description](https://www.disneyanimation.com/process/animation/) emphasizes timing, staging, anticipation, follow-through and weight across subtle and broad movement. Applied here, that supports evaluating controlled amplitude and recovery, not making OSCAR quieter by default. The supplied GIFs lack the temporal character evidence needed for that judgement. These references contextualize the frozen assessment; no borrowed artwork or new acceptance claim is introduced.

## What is worth keeping

The object-only compact design is substantially better than the earlier A/B/C cards. It puts the recognizable shell/puck back at the center of presence without making a giant mascot. Preserve that change.

The leaf has a disciplined information hierarchy. Work, failed, offline and unresolved states have direct titles and a single appropriate route to detail. [Offline](fixture-offline-expanded-1.png) explicitly says that work status is unknown and new requests are disabled. [Approval](fixture-approval-expanded-1.png) distinguishes opening from granting approval. [Waiting](native-awaiting-result.png) avoids claiming ongoing execution. These are useful product choices, though pixels alone do not verify the source-bound authority implementation.

The captured accessibility equivalents remain understandable without ornamental effects. Forced colors retain readable text/boundaries and reduced-motion rest retains state. They support those captured states; they do not certify all transitions, assistive technology or native system-settings integration.

### P1 — A blocked native Ask has no visible outcome or recovery

**Independent actual-native evidence:** [14-native-blocked-no-feedback.png](independent-evidence/14-native-blocked-no-feedback.png). In an authenticated disposable Core run, a prior `2 + 3` task reached verified result `5`. The fixture worker was then explicitly disconnected while Core remained online. Ask again restored the composer; clicking Ask produced the authoritative Core response `{state: 'blocked', message: 'Core/Worker capability unavailable or ambiguous; nothing executed', task_id: null}`. The store contained only the prior verified task and no new execution. The settled native sheet nevertheless remained on the composer with `Here`, input `2 + 3`, enabled Ask and **no blocker explanation**.

**Impact:** the user cannot distinguish accepted work from an ignored click, unavailable executor or failure. Repeated clicks become likely and the owner has no visible route to repair/retry. Core correctly refuses execution; this is a presentation/feedback failure, not a claim that Core falsely executed or verified work.

**Correction:** surface the authoritative blocked/message outcome in the current leaf at the narrow presentation boundary, retaining draft and a truthful recovery route. Keep Core reachability distinct from executor availability and preserve unknown/blocked/failed semantics. Do not fabricate Working, create a fake task or reinterpret the blocker as success. The response-plus-interface pairing establishes the missing outcome; this final reviewer has not independently traced the responsible source path.

**Acceptance:** repeat controlled worker disconnect with Core online and assert no new execution plus an immediately visible reason/recovery. Cover no-task blocked responses, expired capabilities and failure messages in a focused UI regression; preserve the successful actual-native result path and disabled offline path. Verify the state stays visible after polling and draft/retry remain usable.

### P1 — Ordinary native reinvocation leaves a persistent confirmation warning

**Independent actual-native evidence:** [07-native-reinvoke-warning.png](independent-evidence/07-native-reinvoke-warning.png). The actual online Tauri run followed rest → Orb click → targeted editor entry → Escape → Ctrl+Alt+O. The draft was retained and the sheet reopened. On a settled second observation, the sheet still displayed `Window confirmation expired. Try opening the presence again.` even though `Here` remained current, the draft was visible and Ask was enabled. No Core loss was injected. The extra warning crowded the small leaf and introduced a vertical scrollbar.

**Impact:** an everyday recovery path tells the user to reopen a surface that already appears open. This weakens reliability, adds ambiguous error state and obstructs the intended fast writing/recovery flow. It is more consequential than the caption/focus finish findings. The observation proves a persistent warning in this native sequence; it does not prove the precise failure or reconciliation mechanism.

**Correction:** investigate native window acknowledgement/event ordering and state reconciliation, then fix the narrow responsible layer. Distinguish genuine unsatisfied resize/focus requests from stale/equal confirmation events or already applied state. Clear the message only after the correct native state is authoritatively established, and ensure genuine rejected/expired requests still produce an accurate, recoverable state. Do not hide errors cosmetically or weaken the generation/freshness boundary.

**Acceptance:** replay this exact actual-native sequence repeatedly with a disposable Core: text retained, requested size/state read back, no stale warning in the successful case, immediate usable input, accurate warning/recovery in an intentionally failed case. Include rapid retreat/reinvoke and both event-before-reply/reply-before-event ordering in a focused regression. This review performs no implementation fix and does not use the earlier tests as proof that this newly observed case works.

**Acceptance:** actual Tauri desktop capture at intended compact size, with visible trigger/state timeline and enough temporal samples to evaluate anticipation, overshoot, settling and interrupt priority.
